# تدقيق إدارة المستخدمين لصاحب المدرسة

## الحالة الحالية

إدارة المستخدمين لحساب `school_owner` غير مكتملة، ولا ينبغي فتح واجهتها قبل إضافة قيود الخادم المطلوبة.

| الوظيفة | الحالة الحالية | النقص المطلوب قبل التفعيل |
|---|---|---|
| عرض مستخدمي المدرسة | الـAPI يعيد مستخدمي المدرسة نفسها، لكن صفحة `/users` والـSidebar محصورتان بـ`system_admin` | إضافة Route Guard وواجهة مخصصة بعد تثبيت القيود أدناه |
| إنشاء حساب موظف | محصور بخادم `requireAdmin()` وواجهة `system_admin` | السماح لـ`school_owner` مع إجبار `school_id` على مدرسته ومنع `system_admin` و`school_owner` |
| تعديل الحساب والدور | محصور بخادم `requireAdmin()` | التحقق من أن الحساب المستهدف والدور الجديد تابعان لنفس المدرسة ومن قائمة الأدوار المسموحة |
| تفعيل/تعطيل الحساب | محصور بخادم `requireAdmin()` | منع استهداف مدرسة أخرى، ومنع تعطيل حسابات محمية أو حساب المالك نفسه دون سياسة واضحة |
| إعادة تعيين كلمة المرور | محصورة بخادم `requireAdmin()` وتقبل كلمة مرور يحددها المدير | إنشاء كلمة مرور مؤقتة فقط، وتخزين حالة تجبر المستخدم على تغييرها عند الدخول التالي |

## القيود الأمنية المطلوبة

1. يثبت الخادم مدرسة `school_owner` من جلسة المصادقة، ولا يثق بقيمة `school_id` المرسلة من الواجهة.
2. لا يستطيع `school_owner` إنشاء أو تعيين الدورين `system_admin` و`school_owner`.
3. كل قراءة أو تعديل أو تفعيل أو إعادة تعيين يجب أن يرفض المستخدم التابع لمدرسة أخرى.
4. لا تُعاد كلمة المرور القديمة أو تجزئتها في أي استجابة. تم إصلاح استجابة تفاصيل المستخدم في هذا الفرع لإرجاع حقول آمنة فقط.
5. إعادة التعيين تحتاج كلمة مرور مؤقتة مولدة من الخادم، وحقلًا مثل `must_change_password` مع تدفق تغيير إلزامي بعد تسجيل الدخول.
6. ينبغي تسجيل عمليات الإنشاء وتغيير الدور والحالة وإعادة التعيين في سجل تدقيق.

## قرار هذا الفرع

لا يفتح هذا الفرع صفحة `/users` لصاحب المدرسة، لأن فتحها دون القيود السابقة سيمنح واجهة غير مكتملة فوق API لا يدعم التفويض المطلوب. يقتصر التغيير الأمني الحالي على منع تسريب `password_hash` وفرض المصادقة على تفاصيل المستخدم، بينما تبقى إدارة المستخدمين الكاملة لتغيير مستقل مع migration واختبارات API مخصصة.
